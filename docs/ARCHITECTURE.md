# Архитектура «Карты пространства»

## Формат продукта

Одно веб-приложение (PWA), без нативного. Кейс требует, чтобы организатору хватало браузера и камеры телефона, а посетитель открывал карту по ссылке или в iframe на сайте площадки. Всё нужное есть в мобильном браузере: `getUserMedia`, `DeviceOrientation`, WebGL, Service Worker, установка на экран.

## Схема

```
Посетитель (телефон)                        Организатор (телефон / ПК)
┌──────────────┐                             ┌──────────────────────────┐
│ viewer (PWA) │                             │ studio: редактор, съёмка │
└──────┬───────┘                             └────────────┬─────────────┘
       │ только статика: manifest → bundle, тайлы         │ REST
       ▼                                                  ▼
     CDN ◄── STORAGE_DIR (кадры, планы, тайлы) ◄──── API (FastAPI) ── PostgreSQL + PostGIS
                         ▲                                │
                         └──── worker (Python) ◄──── очередь Redis
                               склейка · тайлы · сборка карты и графа
```

Посетитель не ходит в API за картой: только неизменяемые файлы с CDN. Карта открывается быстро и работает, даже если API недоступен.

Один адрес на всё: карта посетителя `/`, студия `/studio/`, API `/api`, файлы `/media` (Caddy в продакшене, сервер Vite карты в разработке проксирует студию). Поэтому ссылки и QR из студии всегда совпадают по протоколу и порту со страницей, на телефоне подтверждается один сертификат, cookie — same-origin. Адрес для ссылок: `VITE_PUBLIC_URL`, иначе адрес страницы (localhost заменяется LAN-адресом машины).

## Модель данных

По мотивам IMDF (Apple, OGC Community Standard):

| Сущность    | Что это                                                                                                                                                                       |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Venue`     | площадка; якорь локальной системы координат; оформление (`branding`), объявления, свои категории точек, часовой пояс (`timezone`, IANA), языки                                |
| `Building`  | здание (их может быть несколько)                                                                                                                                              |
| `Level`     | этаж: `ordinal`, имя, высота                                                                                                                                                  |
| `Unit`      | помещение / коридор / лобби — полигон, категория, `walkable`, `access` (public / staff / closed); высота потолка, цвет, описание, фото, вместимость, удобства, часы, переводы |
| `Opening`   | дверь / проход / вход / окно — отрезок на границе `Unit`; `access` (public / staff / emergency / locked), тип и ширина двери; у окна — подоконник и высота                    |
| `Connector` | лестница / лифт / эскалатор / пандус — связывает этажи                                                                                                                        |
| `Poi`       | точка интереса: название, категория, описание, высота над полом; фото, ссылки, контакты, часы, теги, «главное», события (расписание), переводы                                |
| `Fixture`   | мебель и оборудование внутри помещения (IMDF fixture): стол, стенд, сцена, стойка, колонна… — препятствие для маршрутов (`obstacle`), высота для 3D                           |
| `Zone`      | подписанная область внутри помещений (фудкорт, зона тишины): цвет, описание; на маршруты не влияет                                                                            |
| `Pano`      | панорама: позиция, этаж, `heading`, `cameraHeight`, статус, ссылки на тайлы                                                                                                   |
| `PathLine`  | уличная дорожка (ручная или из OSM)                                                                                                                                           |
| `NavGraph`  | производный: узлы и рёбра с флагами (`stairs`, `elevator`, `outdoor`, `barrier`)                                                                                              |

Черновик карты — документ (JSONB). Сохранение запускает сборку неизменяемой версии `map_versions`. `maps.published_version_id` указывает на актуальную.

Правила схемы (`packages/map-schema`, `schemaVersion` 2): всё, что добавлено после первой версии, необязательно — старые черновики и опубликованные бандлы остаются валидными, а проверка старого документа поднимает его версию. Поля со значением по умолчанию не попадают в JSON (`exclude_if`), так что карта без новых функций не растёт в размере. Документ — пользовательский ввод, который уходит посетителям: тексты ограничены по длине и без служебных символов, ссылки — только `https://` (картинки) / `http(s)://` (ссылки) или наш `/media/` без `..`, цвета `#RRGGBB`, время событий — ISO 8601 со смещением, часовой пояс проверяется по базе IANA. Ошибки — с типом `map_*` и понятным текстом для редактора. Схемы проверки и сериализации совпадают, поэтому в OpenAPI один тип `MapDocument`.

## Публикация и доставка

- Сборка версии (сейчас синхронно в API): черновик + готовые панорамы → неизменяемая версия (`map_versions.bundle`). Дальше в воркер переедут граф маршрутов, видимость точек и поисковый индекс.
- Бандл видимой всем карты — статический файл `/media/maps/{map_id}/v/{n}/bundle.json` (и `.gz` рядом): пишется при публикации, Caddy и CDN отдают его без Python и кэшируют навсегда. Путь — по id карты, а не по slug: адрес, отданный потом другой карте, никогда не попадёт на старую копию в кэше. Версии, опубликованные раньше, получают файл при первом запросе манифеста.
- Карты «только участники» статического файла не получают: их бандл идёт через `/api/public/maps/{slug}/v/{n}/bundle.json` с проверкой сессии (`private`). Этот же адрес работает для старых манифестов и офлайн-копий. Перевод в «только участники» сразу удаляет статические версии карты (копии, уже попавшие в CDN, живут до его сброса), обратный перевод снова пишет файл текущей версии. Публикация, смена режима и создание файла по манифесту берут блокировку строки карты, поэтому файл закрытой карты не может появиться снова.
- `manifest.json` по ссылке `/m/{slug}`: `no-cache` + ETag (повторное открытие — 304 без тела), указывает на версию; у закрытых карт `private, no-cache`. Файлы версии — `Cache-Control: immutable`.
- Живые статусы мест (`map_live`: открыто / очередь / закрыто и заметка до 140 символов) меняются без публикации: организатор — `PUT/DELETE /api/maps/{id}/live/{poi}` (право «редактировать», только для точек, которые есть на карте), посетитель опрашивает `/api/public/maps/{slug}/live.json` (`public, max-age=15` + ETag; у закрытых карт — только участникам).
- Статика студии и карты сжата при сборке образа (brotli 11 и gzip 9 рядом с файлами, Caddy отдаёт готовые), HTTP/3.
- Ссылка не меняется при сохранении, откат на прошлую версию — переключение указателя.
- Состояние в URL: `/m/{slug}?level=2&poi=…&from=…&to=…&pano=…` — маршрутом можно поделиться.
- Встраивание: `<iframe allow="fullscreen; accelerometer; gyroscope">` + `embed.js` (postMessage API). Разрешённые домены — `frame-ancestors` на карту.

## Панорамы

### Съёмка (studio, браузер)

- Экран в стиле Photo Sphere: сфера с точками-целями, прицел. Кадр делается автоматически, когда прицел совпал с целью и угловая скорость по гироскопу мала.
- Сетка: кольцо по горизонту + вверх + вниз + зенит/надир ≈ 25–30 кадров основной камерой; ~15 широкоугольной (если браузер её отдаёт в `enumerateDevices`).
- С каждым кадром — кватернион ориентации (соглашение в `CLAUDE.md`), время, ориентация экрана.
- Android: `ImageCapture.takePhoto()` для полноразмерных кадров; iOS: кадры из видеопотока (запрашивать ideal 4K). 1080p в портрете ≈ 8K итоговой панорамы.
- Отбраковка смаза (дисперсия Лапласиана в Web Worker), Wake Lock, подсказки по технике съёмки.
- Кадры → IndexedDB → загрузка с повторами. Живой предпросмотр: раскладка кадров на сферу по датчикам (three.js).

### Склейка (worker)

1. Начальные повороты — из датчиков.
2. Пары для сопоставления — только соседние по датчикам.
3. Признаки: SIFT; при наличии GPU — ALIKED + LightGlue.
4. Bundle adjustment поворотов и фокуса со штрафом за отклонение от датчиков (`scipy.optimize.least_squares`) — на белых стенах держимся за гироскоп.
5. Горизонт — по гравитации из датчиков.
6. Экспокомпенсация, graph-cut швы, multi-band blending.
7. Надир — inpaint или логотип организатора.
8. Выход: equirect 8192×4096 → тайлы.

Запасной вариант для сравнения: Hugin CLI (`pto_gen` → `cpfind --prealigned` → `autooptimiser -a -m -l -s` → `nona`/`enblend`) с начальными углами из датчиков.

Готовые панорамы: equirect 2:1 и GPano XMP (частичные сферы). Всё перекодируется pyvips.

### Доставка и просмотр

- Превью 512 px (~20 КБ, сразу) → уровни 2K/4K/8K тайлами 512 px в WebP (pyvips).
- PSV `EquirectangularTilesAdapter` грузит только видимые тайлы. Превью соседних панорам — заранее.
- Плагины PSV: Markers (точки, маршрут на полу), VirtualTour (переходы), Gyroscope.

## Связка план ↔ панорама

- Точка на плане автоматически появляется в панорамах, откуда видна: `yaw = bearing − heading`, `pitch = atan2(Δh, d)`, видимость — отрезок не пересекает стены (границы `Unit` минус `Opening`). Ручная правка хранится как override на паре (pano, poi).
- Тап по полу в панораме → точка на плане: `d = cameraHeight / tan(−pitch)`.
- Стрелки переходов — к соседним панорамам в прямой видимости.
- Маршрут на полу внутри панорамы — проекция линии маршрута (Markers polyline).

## Маршрутизация

- Граф строится на клиенте из опубликованного бандла (`packages/map-core/src/routing`), без отдельного шага на сервере: это миллисекунды для площадки на сотни комнат, работает офлайн и сразу после публикации. Узлы — двери, точки подхода к двери внутри каждой комнаты (0,9 м от стены, чтобы путь не прижимался к стене), точки, коннекторы, внутренние углы комнат с отступом 0,9 м. Внутри `Unit` — рёбра по прямой видимости (отрезок проверяется на выход за контур). Коннекторы связывают этажи; `walkable: false`, `nonpublic` и помещения с `access` staff / closed не проходятся; окна и двери с `access` не public в граф не попадают.
- Мебель (`Fixture` с `obstacle`) — дыры в полу помещения: прямая не пересекает препятствие и держится от него не ближе 0,35 м, вокруг выпуклых углов ставятся узлы в 0,45 м (проход между столами — от ~0,8 м). Точка внутри препятствия (стенд, сцена) — тупик: маршрут туда приходит, но насквозь не идёт. Препятствия раскладываются по помещениям заранее; площадка на ~200 комнат и 100 столов строится за ~75 мс.
- «Без ступенек» также не ведёт через вращающиеся двери и двери уже 0,8 м (`widthM`).
- Поиск пути — Дейкстра на бинарной куче. Стоимость — метры плюс штраф за смену этажа (лестница 8, эскалатор 6, пандус 4, лифт 25 + 3 за этаж). «Без ступенек» исключает лестницы и эскалаторы; если иначе не пройти — посетитель видит причину.
- Подсказки: «Пройдите через дверь в «Коридор» и поверните направо», «Поднимитесь по лестнице на 2 этаж», «Вы на месте»; расстояние и время (1,2 м/с, плюс время на этаж).
- На плане: линия маршрута по этажам, метки старта, финиша и смены этажа («↑ 2 этаж» / «с 1 этажа»), автоподгонка под маршрут; нажатие на шаг показывает его на плане.
- «Пройти по панорамам»: панорамы не дальше 4 м от линии, по порядку движения; взгляд — вдоль линии маршрута (а не на неё, если панорама стоит сбоку), линия на полу — polyline-маркер, следующая панорама подписана «Дальше по маршруту», есть автопроход.
- Начальная точка: поиск, тап по плану (только внутри помещений), QR-метка «Вы здесь» (`?here=<poiId>`, печатается на странице «Поделиться»). GPS на улице — следующий шаг.
- Студия проверяет связность: комнаты без дверей, точки, до которых не дойти, этажи без лестницы.

## План и редактор

- MapLibre: подписи без наложений, иконки по категориям, 3D-стопка этажей (`fill-extrusion`), heatmap статистики.
- Геопривязка: территория, несколько зданий, GPS, подложка OSM (self-hosted PMTiles, вырезка района). Глифы с кириллицей — свои.
- Terra Draw: полигоны, прямоугольники, выделение/поворот/масштаб, привязка; свои режимы: «стены → комнаты» (`polygonize`), двери на стенах, привязка к прямым углам.
- Импорт: PNG/JPG/PDF (pdf.js) как подложка с выравниванием по 2–3 точкам или по известному размеру; DXF (ezdxf).

## Редактор плана

- Панели как в картографических редакторах: слева сверху меню, название, этаж; справа сохранение, «Поделиться», команда, «Опубликовать», аккаунт; снизу инструменты, слои, отмена, масштаб, справка; справа — свойства выбранного.
- Инструменты (цифры слева направо): 1 выбор, 2 перемещение, 3 комната (два клика), 4 контур, 5 дверь (клик по стене, тип в стрелке), 6 лестница/лифт (связь с этажом выше), 7 точка (категория в стрелке, ставится подряд), 8 мебель, 9 дорожка, 0 панорама. Загрузка плана и привязка — кнопки рядом.
- Привязка (`studio/src/lib/snap.ts`): к углам соседних комнат, затем к стенам, затем к сетке 0,5 м; прямоугольники следуют повороту подложки; дверь встаёт по центру ближайшей стены нужной ширины.
- Комнаты и точки рисуются подряд без возврата к «Выбору»; точки и панорамы перетаскиваются.

## Роли и команда

Четыре роли на карту (владелец, редактор, съёмщик, наблюдатель), права — в `api/permissions.py`. Участники добавляются по email или по ссылке-приглашению (подписанный токен на неделю, роль зашита в токен, приглашение не понижает уже выданную роль). Профиль: имя, смена пароля (остальные сеансы завершаются), выход на всех устройствах.

## Офлайн

- Посетитель: сохранение карты целиком в Cache Storage (`offline-maps`), список «Мои карты» в IndexedDB, свой service worker отдаёт сохранённое раньше сети, обновление при новой версии, `navigator.storage.persist()`.
- Организатор: очередь кадров съёмки в IndexedDB с бесконечными повторами при обрыве и восстановлением после перезагрузки; локальная копия правок плана и повтор автосохранения.

## Безопасность

- studio (`/studio/`, только после входа) и viewer (`/m/…`) — разные бандлы на одном адресе. CSP собирается при сборке образа (`infra/web/csp.mjs`): `script-src 'self'` + sha256 inline-скриптов именно этой сборки, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `connect-src` — свой адрес и шрифты protomaps. У студии `frame-ancestors 'none'`, `X-Frame-Options: DENY` и `Cross-Origin-Opener-Policy: same-origin`; карту можно встраивать (`frame-ancestors *`). Ответы API — `default-src 'none'`.
- CSRF: каждый изменяющий запрос (POST/PUT/PATCH/DELETE) с заголовком Origin — и без сессии тоже, это защита от login CSRF — принимается только со своего адреса (Host / X-Forwarded-Host) или из `CORS_ORIGINS`. Браузер всегда шлёт Origin с такими запросами, поэтому запрос без Origin — не браузер (скрипт, сервер-сервер) и проходит. Второй слой — SameSite=Lax.
- Сессия: httpOnly cookie `__Host-ttk_session` (Secure, Path=/, без Domain — соседний поддомен не может подложить или перезаписать её; имя меняется через `SESSION_COOKIE`). При входе удаляются истёкшие сессии пользователя.
- `/media`: Caddy сам отдаёт только `panos/` и `maps/` из тома хранилища, смонтированного только для чтения (имена — буквы, цифры, `._-`, без скрытых файлов; `..`, `%` и `\` в исходном URI — 404). Сырые кадры, видео и сканы комнат (`captures/`, `scans/`) не раздаются. В dev то же проверяет API; ключи хранилища проверяются лексически (без обращений к диску), запись файлов атомарная (временный файл + rename).
- `SECRET_KEY` обязателен в продакшене (иначе API не стартует); приглашения не дают роль владельца даже по поддельному токену.
- Изображения: проверка размера в пикселях до декодирования (защита от «бомб распаковки»), тяжёлое перекодирование и argon2 — в пуле потоков, не в цикле событий.
- Размеры тела: к API в Caddy — до 30 МБ, видео (панорама из видео, скан комнаты) — до 320 МБ (сам файл — до 300 МБ), черновик — до 5 МБ; API отвечает 413 до разбора тела (по Content-Length или по ходу приёма chunked-тела).
- Видео: сигнатура WebM/Matroska (EBML) или MP4/MOV (`ftyp`, фото HEIC/AVIF отклоняются), multipart разбирается только после проверки доступа — без права на съёмку нельзя заставить сервер принять 300 МБ; файл копируется потоком (не в память), соединение с базой на время приёма отпускается. Дорожка ориентации проверяется схемой и сохраняется пересобранной.
- Лимиты запросов — скользящее окно в Redis, общее для всех процессов uvicorn (`WEB_CONCURRENCY=2`); если Redis недоступен, счёт идёт в памяти процесса, запросы из-за этого не падают. Вход — по паре IP + email (на площадке все за одним NAT) и мягкий лимит по IP; регистрация, смена пароля, события статистики; загрузка видео — 30 за 10 минут на карту с одного адреса. Dev-базы слушают только 127.0.0.1.
- Вход: email + пароль (argon2id), Яндекс ID / VK ID. Роли на карту: владелец, редактор (инвайт).
- Режимы карты: публичная / по ссылке (неугадываемый slug) / только участники. «По паролю» пока не реализован: API отвечает 422, а карта, у которой он уже записан, отдаётся только участникам (закрыто по умолчанию). Закрытые тайлы — по коротким подписанным URL (следующий шаг).
- Загрузки: через API с проверкой сигнатуры и размера, перекодирование (без EXIF/GPS). Съёмка с телефона — по подписанному токену на одну карту (HMAC, 2 часа, в фрагменте URL из QR). Параллельные загрузки кадров одной панорамы не теряют кадры: список кадров обновляется под блокировкой строки (`SELECT … FOR UPDATE`). Оптимистичная блокировка при сохранении черновика (409).
- Сервер: лимиты памяти у каждого контейнера (воркер — 2,5 ГБ и 1,5 ядра, параллельно одна задача), ротация логов, Postgres настроен под 700 МБ. Бэкапы — `infra/deploy/backup.sh` (pg_dump + снимок тома на жёстких ссылках, 7 дней, по cron), закалка — `infra/deploy/harden-server.sh` (автообновления безопасности, fail2ban для SSH, вход только по ключу — отдельным флагом).

## Мобильные подводные камни

- HTTPS обязателен для камеры и гироскопа, в том числе в dev (туннель или mkcert).
- iOS: разрешение на датчики — только по тапу; нет `screen.orientation.lock` и `ImageCapture`; лимит canvas ~16.7 Мпикс; жёсткие лимиты памяти WebGL → обработка `webglcontextlost`.
- `100dvh`, `env(safe-area-inset-*)`, `overscroll-behavior: none` на карте, `touch-action` на холстах.
- Гироскоп в cross-origin iframe на iOS может не работать → кнопка «на весь экран».
- Офлайн на iOS надёжен только для PWA, установленной на экран; `navigator.storage.persist()`.

## Порядок работ

1. Модель данных, заготовка репозитория, деплой с HTTPS. Параллельно — прототип съёмки и склейки на 3–4 реальных комнатах (главный риск).
2. Редактор плана и точек, публикация, viewer с поиском и карточкой.
3. Загрузка готовых панорам, тайлы, просмотр, переходы, автопроекция точек.
4. Граф и маршрут на плане → маршрут в панорамах.
5. Съёмка с телефона в боевом качестве.
6. Этажи, офлайн, QR, встраивание, статистика.
7. Остальное — по времени.
